# Working Tree Protocol — Standing Rules for Cursor

> Read this before starting any UX prompt. These rules apply to every session.

---

## When you find unexpected changes in the working tree

Before starting any prompt, run `git status` and `git diff --stat HEAD`. If you see
modified files that are not part of your assigned UX prompt, classify each one before
deciding how to proceed.

### Classification guide

| File type | What it usually means | Action |
|---|---|---|
| `next-env.d.ts`, `tsconfig.tsbuildinfo` | Auto-generated by the compiler. Not real changes. | Stage and commit with your work. |
| A 1–5 line change in a layout/nav file (Sidebar, TopBar, etc.) | A small fix or nav correction from a previous session that wasn't committed. | Inspect the diff. If it looks intentional and correct, include it in your commit with a note. |
| A large change in a file unrelated to your prompt | Genuinely unfinished work from a different feature. | Do NOT overwrite or reset it. Leave it staged as-is and flag it in your commit message. |
| Untracked files from your own prompt | Your new files, not yet staged. | Stage and commit as normal. |
| Untracked cursor-prompts/*.md files | Prompt documents — not source code. | Leave untracked. Do not commit them unless explicitly asked. |

### The two-step check

1. **Run `git diff HEAD -- <file>`** on any unexpected modified file.
2. Ask: *"Is this change correct and intentional?"*
   - If yes → include it in the commit, note it in the message.
   - If unsure → include it but flag it explicitly: `// NOTE: pre-existing change, included as found`.
   - If it looks broken or conflicting → stop and report before proceeding.

---

## Do NOT do these things

- **Do not run `git restore .` or `git checkout -- .`** to clean up "dirt" without
  human confirmation. You may discard legitimate in-progress work.
- **Do not reset or hard-reset** any branch without being explicitly told to.
- **Do not skip committing auto-generated files** (`next-env.d.ts`,
  `tsconfig.tsbuildinfo`). They change legitimately when TS config changes and
  leaving them unstaged causes noise on every future `git status`.
- **Do not stop work and ask for direction** just because unrelated files are modified.
  Classify them using the guide above and continue unless you find a genuine conflict.

---

## Commit message format when pre-existing changes are included

```
feat(ux11): room canonical — migration, types, APIs, entity, slide-over

Pre-existing: Sidebar.tsx (dashboard active state fix), SidebarTourPicker.tsx
(nav to /overview not /advance) — included as found, both correct.
Auto-generated: next-env.d.ts, tsconfig.tsbuildinfo — staged as normal.
```

---

## Branch awareness

Always check which branch you are on before starting (`git branch --show-current`).
The canonical development branch is `main`. Feature work happens on prompt-specific
or partner-sync branches. Do not push to `main` directly unless explicitly instructed.

---

## Lint failures

`npm run lint` currently has **repo-wide pre-existing lint issues** unrelated to the
UX prompts. A lint failure alone is not a blocker. The gate is:

1. `npx tsc --noEmit` passes — **required before committing**.
2. Lint failures are **only a blocker** if they are in files you have modified.
   Check with `npx eslint <your-modified-files>` to isolate your own issues.
