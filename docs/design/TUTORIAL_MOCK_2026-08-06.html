▸ Implementation notes — the credit-efficient build this render implies
Everything above is one panel + one data file. Nothing here needs per-page bespoke code.
  1. One step registry. A single JSON/TS array drives both modes: {section, mode, targetSelector, caption, task}. The 12 tabs, every coach-mark caption and every checklist task in this mock are literally rows of that registry (see SECTIONS in this file's script — it is the shape of the real registry).
  2. One overlay component. A single spotlight+tooltip component reads targetSelector from the registry and positions itself over the live page — the grey-box frames in this mock stand in for "the real page, spotlit". No per-surface walkthrough code; adding a step = adding a registry row.
  3. One mount point. The panel mounts once in the app shell (same layer as ⌘K, --lp-z-modal) and is opened from one new item in the avatar menu — the highlighted App tour & tutorial row shown top-right. That menu item is the only nav change.
  4. Progress = one column. Per-user progress is a single JSONB column on profiles (e.g. tutorial_state: {mode, section, doneTasks[]}), mirrored to localStorage for instant resume. No new tables.
  5. Tutorial data is REAL data. "Weekend Away" is created through the existing artist/tour/routing/rider/budget APIs with a practice: true flag on the tour — so every page behaves identically to production and there is zero mock-data plumbing. Finish screen offers keep-or-delete (one cascade delete on the flagged tour).
  6. Task detection is cheap. Checklist items verify via the same selectors/queries pages already use (e.g. "2 show days exist" = the routing count already in the rail badge). Anything hard to detect stays a manual checkbox, exactly as rendered here.
Net: 1 registry + 1 overlay component + 1 menu item (+ 1 profiles column). Tour mode and Tutorial mode are the same machinery with mode flipped.
