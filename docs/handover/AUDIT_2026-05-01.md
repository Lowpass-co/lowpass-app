After Phase 3 lands, the dual-surface problem partially survives. Verify in the Phase 3 PR review; if it's missed, add to the Phase 3 fix-up.

## §2. Database & migrations

The 04-30 SQL drift audit and the RLS discovery doc are still the master reference. This audit confirms what's open:

### 2.1 Seven duplicate migration numbers — UNRESOLVED. Severity: high.

```
017  017_budget_system.sql                + 017_024_combined_budget_system.sql
018  018_advance_templates_sort_order.sql + 018_profiles_job_title_phone.sql
019  019_advance_layout_templates_workspace.sql + 019_storage_avatars_bucket.sql
024  024_profiles_extended.sql            + 024_rich_line_items.sql
025  025_personnel_roster_link.sql        + 025_storage_avatars.sql
026  026_line_item_links.sql              + 026_personnel_extended_profile.sql
035  035_bug_reports_reconcile.sql        + 035_rental_jobs_billing_details.sql
```

A future migration runner will silently apply only one of each pair. The `chore/migration-renumber` and `fix/migration-renumber` branches exist locally but neither is on origin under that name (origin has `fix/ux12-migration-renumber` and `fix/migration-renumber`). State of those branches relative to this issue is unverified. Cleanup is its own PR — don't bundle.

### 2.2 Three orphan tables in production. Severity: high.

`rental_inventory`, `rental_jobs`, `rental_job_items` — referenced by code, ALTER'd by migrations 028/035/057, but no `CREATE TABLE` statement anywhere in `database/migrations/`. Direct-pasted into prod historically. A fresh-clone bootstrap produces a database that fails on Equipment routes.

The RLS discovery doc deferred RLS work on these because they're user-scoped (not workspace-scoped). The CREATE TABLE problem is independent of the RLS problem and should ship first.

### 2.3 Fourth orphan table: `workspace_members`. Severity: critical.

Not flagged in any prior doc, but verified: `workspace_members` is referenced by `src/lib/api/`, RLS policies in migration 061, and at least 30 supabase calls across the app. **No `CREATE TABLE workspace_members` statement exists in any migration file.** It's not in 001 (initial schema). It only appears in 061's RLS policies as a JOIN target.

Production has it. Fresh clone doesn't get it. This is an even more severe orphan than the rental triplet because workspace membership underpins every RLS policy in the app.

### 2.4 `bug_reports` has duplicate CREATE TABLE — not idempotent in 001

`bug_reports` is created in both `001_initial_schema.sql` and `033_bug_reports.sql`. 033 uses `CREATE TABLE IF NOT EXISTS`, so it's safe. But 001 does NOT use IF NOT EXISTS for any of its 16 tables. A fresh-clone runs 001 cleanly only because the DB starts empty. Re-running 001 against an existing DB errors on every CREATE TABLE.

This is a low-impact issue today (001 only runs on a fresh clone) but bites if you ever try to re-baseline. **Severity: low.** Worth a one-line PR converting all of 001 to `CREATE TABLE IF NOT EXISTS`.

### 2.5 RLS coverage — substantively complete, with two known holes

Per the 04-29 RLS discovery doc and migration 061 plus its §9 extension, every workspace-scoped table in `public.*` has SELECT/INSERT/UPDATE policies. The two documented holes:

- `rental_inventory` / `rental_jobs` / `rental_job_items` — user-scoped, deferred to a separate user-scoped audit pass. Action: write that audit, OR denormalise `workspace_id` onto each table and absorb into the canonical pattern. Adam's product call.
- Storage buckets `budget-files` and `receipts` (or `expense-receipts` — likely a stale string) — bucket creation isn't migrated. `artist-assets` policies exist (007) but the bucket itself is created in the Supabase Dashboard. Fresh-clone → broken file uploads on Budget. Action: add migrations mirroring 016's pattern.

### 2.6 Pending migration: 064 — Severity: medium, gates Phase 3 merge

`database/migrations/064_budget_line_items_phase_tag.sql` exists on `feat/product-split-phase3` but not on `main` (because Phase 3 isn't merged) and presumably not yet applied to production. The CC commit message in `3eb3d37` notes: "Adam: apply migration 064 in Supabase before exercising the Phase dropdown — without the column, the PATCH 400s." This needs to be pasted into Supabase BEFORE Phase 3 merges; otherwise the merged branch's UI will silently fail.

### 2.7 Migration runner is overdue — Severity: high (systemic)

The 04-30 SQL drift audit nailed the root cause: there's no `_lp_migrations` tracking table, no `npm run db:migrate`, no CI verification that fresh-clone bootstrap produces a working DB. Every drift bug traces back to this. The longer it goes unaddressed, the harder the cleanup becomes.

This is the single highest-leverage fix in the database area. A two-day sprint to write a tiny runner, add the tracking table, retroactively populate it for all previously-applied migrations, and add a CI check would prevent the next 12 months of "billing_address column not found" bugs.

## §3. Code health

### 3.1 Lint and types — clean against documented baselines

- `npx eslint src/`: 75 errors / 120 warnings. **Identical to the documented baseline.** No regressions on either feature branch (verified on Phase 3 branch).
- `npx tsc --noEmit`: zero errors outside stale `.next/types` (which references files Phase 3 deleted; clears with a build).

Memory note: `tsc` OOM'd at 2GB. `NODE_OPTIONS="--max-old-space-size=4096"` is needed in this sandbox; presumably also on Adam's MBP if he ever runs typecheck locally without warm caches. Worth a one-liner in a `.npmrc` or the typecheck script.

### 3.2 `any` and `@ts-ignore` — disciplined

- 2 actual uses of `: any` in `src/components/equipment/ImportModal.tsx` (catch blocks). Both `catch (e: any)` — the standard "I don't know what error shape" idiom. Could be tightened to `catch (e: unknown)` but not pressing.
- Zero `@ts-ignore`, `@ts-expect-error`, or `@ts-nocheck` anywhere. Discipline holds.

### 3.3 Dead dependencies — Severity: low.

- `@heroui/react` (~2.8.10) is in `dependencies` and imported zero times. Removing saves bundle size and audit surface.
- `pg` (`^8.20.0`) is in `devDependencies` and imported zero times in `src/`, `scripts/`, or any `.mjs`. Likely a leftover from an experimental migration runner that never landed.

Recommendation: `npm uninstall @heroui/react pg`. Verify nothing breaks via `npm run build` and `npm run typecheck`. Single-commit PR.

### 3.4 The `_legacy/` situation is split, partially leaky. Severity: medium.

CLAUDE.md says: "_legacy/ ← retired pre-overhaul code; do NOT import from here." Reality:

- `src/components/_legacy/sidebar/` — clean. README documents the retirement, has zero importers, exists as reference only. Safe to delete entirely if you want, but it costs nothing where it sits.
- `src/_legacy/budget/` — leaky. 16 files. Active code imports from it in 4 places:
  - `src/components/budget/BudgetTourSelector.tsx` → `pushRecentTourId` from `_legacy/budget/budget-recent`
  - `src/components/budget/BudgetDetailShell.tsx` → re-exports from `_legacy/budget/BudgetDetailShell` (with a `@deprecated` comment, but it's still re-exporting)
  - `src/lib/shell/rails/budgetSheetSections.ts` → `BUDGET_TABS` from `_legacy/budget/budget-tabs`
  - `src/app/(app)/budget/page.tsx` → `BUDGET_TABS, TabId` from `_legacy/budget/budget-tabs`

The CLAUDE.md rule is being violated by load-bearing code. Phase 3 may resolve this (it ships a new BudgetSpreadsheetView and BudgetSummaryTab) — verify when the Phase 3 PR opens. If Phase 3 leaves the `_legacy/budget/` imports in place, that's a Phase 3 fix-up.

### 3.5 Two budget shells coexist (related to §1.2)

- Old: `src/app/(app)/budget/page.tsx` + `BudgetDetailShell` + `_legacy/budget/*` tabs.
- New: `src/app/(app)/budget/[tourId]/page.tsx` (placeholder; real on Phase 3 branch).

After Phase 3 merges, plan a follow-up commit to delete the old `/budget/page.tsx` if Phase 3 doesn't cover it. The handover's redirects intentionally don't catch the query-string surface, so deletion is the right move once the new path is fully populated.

### 3.6 Two shell systems coexist — expected, but worth noting

- 17 pages use `ProductShell` (shell-v2): the new product-prefixed routes plus Home and a couple of workspace-level surfaces.
- 44 pages use `PageShell` (shell-v1, UX02-era): the rest.

Phase 4 (Operations migration, not yet started) will swing more pages over. The two shells coexist cleanly today — they don't share state in a way that conflicts. But until Phase 4 ships, anyone touching pages in the old `/tours/[id]/*` or `/library/*` routes will be writing PageShell code that's future-deletion bait. Worth noting in CLAUDE.md.

## §4. UX & visual consistency

### 4.1 JS string-concat of CSS vars — clean

Zero hits on the `'var(--lp-orange)' + '1a'` anti-pattern across `src/`. The lesson took.

### 4.2 Hardcoded hex outside tokens — 202 instances. Severity: medium.

After excluding the explicitly-allowed `#FF4500..` brand-orange variants, there are 202 hardcoded six-digit hex colours in `src/`. Top concentrations:

- `src/app/(auth)/login/page.tsx` (31) — auth surface; some defensible (Google OAuth button branding can't use vars), some likely over-applied.
- `src/lib/theme.ts` (20) — almost certainly the palette definition itself; legit.
- `src/components/equipment/exportJobPdf.ts` (13) — PDF export; jspdf can't read CSS vars, so hex is unavoidable.
- `src/components/rider-pack/SubSnakeDialog.tsx` (10) — cable-diagram colours; product-meaningful, may need a token group.
- `src/components/bug-report/types.ts` (10) — likely status colour map; should reference `--color-lp-status-*`.
- `src/components/tours/TourOverviewClient.tsx` (8) — surface that's about to be ported in Phase 4; not worth fixing now.
- `src/components/advance/ApplyAdvanceTemplateSlideOver.tsx` (8) — worth a sweep.
- `src/app/(app)/artists/[id]/page.tsx` (7) — Home page calendar.

The Home calendar is the most interesting. Lines 386-393 define a six-colour palette for tour disambiguation: `#3B82F6` (blue), `#8B5CF6` (purple), `#EC4899` (pink), `#10B981` (green), `#F59E0B` (amber), `#EF4444` (red). The handover's visual locks say "No purple, no blue, no gradients." Calendar disambiguation is a real product need, but the implementation directly contradicts the visual lock. Action: add a `--lp-tour-color-{1..6}` token sequence in `globals.css` using brand-aligned hues, swap `TOUR_PALETTE` to `var()` references. Same accessibility win (distinguishable colours), no lock violation.

### 4.3 Density / mono utility uptake — uneven. Severity: low.

- `.lp-mono` and `.lp-dense` together: 35 hits across `src/`. Reasonable.
- `.lp-stat-value` and `.lp-stat-label`: 5 hits. Low. The Home page should be using these for its stat tiles; verify in the Phase 1 fix commit (`9514ca8`).

The handover's density rule (12px tables/lists, 13–14px detail surfaces, mono on numerics) is followed in spirit but not enforced anywhere. Down the line, an ESLint rule that flags raw `font-size:` values without a token reference could lock this in.

### 4.4 Product-lock violations — clean.

- "Mark All Complete" / "Tasks Done" framing: zero hits in `src/`.
- Checkbox styling on advance fields: the 6 `<input type="checkbox">` matches in `src/components/advance/` are all in selection contexts (multi-select for copy/template-apply/bulk-status flows), not field-completion contexts. Safe.
- Photo-evidence capture: not present.
- "Receipts" / "expense receipts" strings — there's a stale `receipts` bucket reference in some callers (per the 04-30 drift audit §4); separate from product-lock concerns.
